# Ostiary v0.3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Ostiary v0.3.0 with these changes:
- graceful drain on stop, restart and upgrade;
- a `strict` profile;
- a single-daemon lock;
- approved SSH port tunnels;
- Telegram approvals;
- a UX bundle.

**Architecture:** Every feature extends what is already there:
- Profiles are defined in `internal/policy`.
- The daemon lifecycle lives in `internal/daemon` (`daemon.go`, `update.go`, `service.go`).
- The approval queue is `internal/approval`.
- SSH connections are pooled in `internal/sshconn`.
- The UI is `internal/ui`.
- Telegram is a new package, `internal/telegram`. It talks to the daemon through small interfaces and is wired up in `cmdDaemon`, the same way `SetSetup` is wired.

**Tech Stack:** Go 1.26, standard library plus the existing dependencies (`golang.org/x/sys` for file locking). Vanilla JS and CSS.

**Spec:** `docs/superpowers/specs/2026-11-16-ostiary-v0.3-design.md`. Read the section each task cites. The spec text is binding.

## Global Constraints

- Agents must never get a new way to approve, unlock, stop, upgrade, pair or administer. New state-changing human operations go through Begin→Admin. Telegram can resolve *agent requests* only, never admin operations.
- New agent-facing commands (`tunnel open/list/close`) are allowed for agents. Opening a tunnel always requires approval.
- Exit codes:
  - 100 blocked
  - 101 denied or timed out
  - 102 daemon down or vault locked
  - 103 restarting (new)
- Test-only URL overrides (Telegram API) exist only in files with the `e2efake` build tag or in `_test.go` files. Release binaries must not contain the string `OSTIARY_E2E`.
- UI:
  - CSP `default-src 'self'`.
  - No `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `document.write`.
  - No inline scripts or styles.
  - Agent, remote or Telegram-provided text is set with `textContent` only.
  - Copy is in Vietnamese.
- No new Go module dependencies. Do not edit `docs/`. Keep `README.md` current for every feature you add.
- Commit as ASromancer. End every commit message with a blank line and then `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Do not push.
- Full checks (every task):
  - `export PATH=$HOME/.local/sdk/go/bin:$PATH`
  - `gofmt -l .` prints nothing.
  - `go vet ./...` passes, also with `GOOS=darwin`, `GOOS=windows` and `-tags e2efake`.
  - `go test -race ./...` passes.
  - Node: `node --check internal/ui/static/app.js`, then `internal/ui/testdata/highlight_test.mjs` and `errors_test.mjs`.
  - E2E: `go build -tags e2efake -o /tmp/ostiary-e2e-bin . && python3 scripts/e2e.py /tmp/ostiary-e2e-bin` passes, with the count growing as checks are added.
  - Marker check: `go build -o /tmp/r . && ! grep -qa OSTIARY_E2E /tmp/r`.
- Never touch the user's real config, state, keyring or running daemon. Never call the real Telegram API. A Claude Code hook may block some shell commands; if so, rephrase the command. Never disable the hook.

**Steps:**
- [ ] Write the policy tests first.

- [ ] Write the lock tests first.

  - After release, acquire succeeds.
  - Use two separate `os.OpenFile` handles, because `flock` is per open-file description.
- [ ] Implement the lock.
  - Unix: `syscall.Flock`.
  - Windows: `windows.LockFileEx`.

- [ ] E2E: add a host-level strict check, using the existing e2e config pattern. A mutate command from Claude needs fake approval under strict.

### Task 2: Graceful drain (spec §2)

**Files:**
- `internal/daemon/drain.go` (new), `service.go`, `update.go`, `daemon.go`, `rpc.go`
- `internal/approval/approval.go` (finish all pending with outcome `restart`)
- `internal/cli/cli.go` (code 103: auto-retry once and guidance), `mcp.go`, `human.go` (SIGTERM and SIGINT start the drain; `stop --now`)
- `internal/cli/os_unix.go` (`systemdUnit` gets `TimeoutStopSec=75`) and `packaging/linux/ostiary.service` (kept identical; the existing test enforces it)
- `plugin/skills/ostiary/SKILL.md`, `internal/cli/install.go` (`codexBlock`)
- `internal/ui/static/app.js` (confirm dialog before upgrade or lock when `Status.Running` shows activity)
- `scripts/e2e.py` (+1 drain check)

**Interfaces:**
- `daemon.CodeRestarting = 103`.
- `func (d *Daemon) Drain(ctx context.Context, force bool)`. It is idempotent. It does the following, in order:
  1. sets draining;
  2. waits for in-flight Exec calls (a `sync.WaitGroup` counted around Exec and transfers) until done, `ctx` is cancelled, or 60 s pass, unless `force` is set;
  3. runs `q.CancelAll("restart")`;
  4. kills jobs and tunnels, logging each one;
  5. closes the listener.
- `Shutdown` and `Restart` RPCs take `ShutdownArgs{Force bool}`. The old empty-args call still means `Force=false`.
- `StatusReply.Running struct{Commands, Jobs, Tunnels int}`. Tunnels stays 0 until Task 3.
- `approval.Outcome "restart"`. The audit decision for it is `cancelled`.

**Steps:**
- [ ] Write the daemon tests first, using the existing harness:
  - while an Exec runs `sleep 1` on the test sshd, `Drain` makes a new Exec return 103, and the running one completes with exit 0;
  - a pending approval resolves with outcome `restart`;
  - `force` returns immediately;
  - calling `Drain` twice is safe.
- [ ] Implement `drain.go`, then wire `Shutdown`, `Restart` and the upgrade restart to `Drain`. In `cmdDaemon`, `signal.Notify` for SIGTERM and SIGINT calls `Drain(ctx, false)`.
- [ ] CLI:
  - On a 103 reply, wait 10 s, re-dial and retry once.
  - Print the 103 guidance from the spec.
  - Add `ostiary stop --now`.
  - MCP returns the 103 text.
- [ ] Update the skill, `AGENTS.md` block, MCP instructions and README exit-code lists to include 103.
- [ ] UI:
  - Before `admin("upgrade")`, the lock action and any restart action, read `/api/status`.
  - If `Running` has any non-zero value, show a confirm with the counts and two buttons: "Chờ xong rồi cập nhật" and "Cập nhật luôn". The second sends force; add a `force` field to the upgrade admin call and thread it to `Restart`.
  - Lock does not restart the daemon. Show the confirm for lock only if jobs or tunnels are open, because locking cuts new commands.
- [ ] E2E: start `sleep 3` through `ostiary run`, call `ostiary stop` from the human side (e2e acts as the human), then assert the run exits 0 and the next run gets 102 or 103.
- [ ] Run the full checks and commit: `feat: graceful drain on stop/restart/upgrade (exit 103, cancel pending, wait for running commands)`.

### Task 3: Tunnels backend (spec §5)

**Files:**
- `internal/hosts/hosts.go` (`Tunnels []string`, validated as `host:port` with port 1–65535)
- `internal/sshconn/tunnel.go` (new), `tunnel_test.go`
- `internal/daemon/tunnel.go` (new), `rpc.go`, `service.go` (Status `Running.Tunnels`, drain closes tunnels)
- `internal/approval/approval.go` (`Request.Kind "tunnel"` is displayable; no sticky option for tunnels)
- `internal/cli/agent.go` (`tunnel open|list|close`), `mcp.go` (3 tools)
- `internal/hook/hook.go` (`tunnel` stays agent-allowed; ensure no regressions)
- `scripts/e2e.py` (+1 tunnel check)
- `README.md`, `plugin/skills/ostiary/SKILL.md`

**Interfaces:**
- `sshconn.Pool.Forward(t Target, remote string, ttl time.Duration, onClose func(Stats)) (*Tunnel, error)`.
  - It listens on `127.0.0.1:0`.
  - `Tunnel.Addr() string`, `Tunnel.Close()`, `Tunnel.Stats() Stats{BytesIn, BytesOut, Conns int64}`.
- Daemon RPCs:
  - `TunnelOpen(TunnelArgs{Host, Target, TTL, Env}) (TunnelReply{ID, Local, Until, Code, Msg})`. It blocks for approval exactly like Exec.
  - `TunnelList(Empty) ([]TunnelInfo)`.
  - `TunnelClose(TunnelArgs{ID}) Empty`.
- TTL: default 1 h, maximum 8 h. A target not in `host.Tunnels` returns code 100.
- Approval request fields: Kind `tunnel`, Level `destructive`, Cmd `mở tunnel tới <target> qua <host> trong <ttl>`. Sticky is not allowed. Telegram behaves the same as for destructive.

**Steps:**
- [ ] Write `sshconn` tests first, using the existing in-process test SSH server pattern in `sshconn_test.go`:
  - start an echo TCP server reachable from the test sshd;
  - `Forward`, connect locally, check the echo comes back, check stats;
  - TTL expiry closes the tunnel;
  - `Close` closes active connections.
- [ ] Implement `Forward`. Use `client.Dial("tcp", remote)` for each accepted connection, `io.Copy` both ways, and close on TTL with `time.AfterFunc`.
- [ ] Write daemon tests first:
  - a target that is not allow-listed returns 100 without creating an approval;
  - approve (code mode) opens the tunnel and `List` shows it;
  - deny returns 101;
  - drain closes all tunnels;
  - audit entries are written for open, close and deny.
- [ ] Implement the daemon side, the CLI and the MCP tools. Output format:
  - CLI: `tunnel 7 127.0.0.1:41873 -> db.internal:5432 via vmt_dwh_root until 15:42`.
  - `list`: one line per tunnel.
- [ ] E2E: the e2e sshd host gets `tunnels = ["127.0.0.1:<echo port>"]`. Python runs an echo server. `tunnel open` goes through fake approval, then Python connects to the printed port and checks the echo, then `tunnel close`.
- [ ] Docs: README section "Tunnels" and the skill commands.
- [ ] Run the full checks and commit: `feat: approved SSH port tunnels (CLI, MCP, audit)`.

### Task 5: Telegram backend (spec §6)

**Files:**
- `internal/telegram/telegram.go` (new: Bot API client with `getMe`, `getUpdates`, `sendMessage`, `editMessageText`, `answerCallbackQuery`; long-poll loop; pairing; callbacks), `telegram_test.go`
- `internal/telegram/base_e2efake.go` (env override, `e2efake` tag only)
- `internal/vault` (secrets `telegram-token`, `telegram-chat`, `telegram-user`, settings; reuse the Passwords map or add a small `Settings map[string]string`, whichever fits the vault format best while keeping backward compatibility)
- `internal/daemon/telegram.go` (admin ops `telegram-pair`, `telegram-unpair`, `telegram-settings`; hook into `Queue.Add` and resolve notifications; Sức khỏe check)
- `internal/approval/approval.go` (auth `telegram` accepted by `Resolve`; an `OnResolve` callback so the bot can edit its message)
- `internal/cli/human.go` (wiring)
- `scripts/e2e.py` (+1 check against a fake Telegram server in Python: pair, then approve through a callback)
- `README.md` (setup and threat note)

**Interfaces:**
- `telegram.Bot{Token string; Base string; HTTP *http.Client}`. Base is fixed to `https://api.telegram.org` except in tests and `e2efake` builds.
- `telegram.Service`. It is started with:
  - `Options{Bot, ChatID, UserID int64, AllowDestructive bool, Resolve func(id int, choice string) error, Pending func(id int) (approval.Request, bool), OnPairCode func() string}`.
  - Methods: `Notify(r approval.Request)`, `Resolved(id int, d approval.Decision)`, `Run(ctx)`, `Pair(ctx, code string) (chatID, userID int64, err error)`.
- Admin op `telegram-pair`. It is a two-step flow:
  1. Begin→Admin stores the token after `getMe` succeeds and starts pairing. It returns `r.Out` holding the bot username and the 6-digit code.
  2. The UI polls `GET /api/telegram`, which reports `{Paired, Bot, Pairing, AllowDestructive, LastError}`. The poll loop completes pairing when `/pair <code>` arrives.
- `telegram-unpair` removes the token and the ids.
- `telegram-settings` with Name `destructive-on` or `destructive-off`.

**Steps:**
- [ ] Tests first, against an `httptest` fake Bot API that records requests and serves scripted updates:
  - `getMe` with a bad token gives a clear error;
  - pairing succeeds with the right code from a private chat;
  - a wrong code is counted, and the fifth failure ends pairing;
  - pairing expires after 10 minutes, using an injectable clock;
  - a group chat is ignored;
  - `Notify` sends a message with three or two buttons, depending on level and settings;
  - for destructive requests with `AllowDestructive=false`, the message has no buttons;
  - a callback with the right user, chat and nonce calls `Resolve` with the right choice;
  - a callback with a wrong user, chat or nonce is ignored and the bot answers "không hợp lệ";
  - a callback for a request that is already decided gets the answer "đã xử lý";
  - `Resolved` edits the message;
  - long-poll errors back off and are recorded in `LastError`.
- [ ] Implement. Keep the message text plain, with the command in a `<pre>` HTML block (`parse_mode=HTML`) and every value HTML-escaped. The command is truncated at 3000 characters.
- [ ] Daemon wiring:
  - `Queue.Add` calls `tg.Notify`; resolving any request calls `tg.Resolved`.
  - Resolve uses auth `telegram`.
  - Admin ops are never sent to Telegram.
  - Health check: "Telegram: đã kết nối @bot", or the error.
  - Drain stops the poll loop.
- [ ] E2E: a Python fake Bot API (HTTP server). The e2efake build points the daemon at it with `OSTIARY_E2E_TELEGRAM_URL`. The check runs:
  1. pair: the UI admin path over HTTP, as the existing e2e UI checks do; the fake returns a `/pair <code>` update;
  2. a mutate request under strict;
  3. the fake delivers an approve callback;
  4. assert that the run completes and the audit shows `auth=telegram`.
- [ ] Run the full checks and commit: `feat: approve agent requests from Telegram (pairing, inline buttons, audit)`.
