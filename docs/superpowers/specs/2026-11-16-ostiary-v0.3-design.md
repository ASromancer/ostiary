# Ostiary v0.3: design

- Date: 2026-11-16
- Status: scope approved by the user. The user picked Telegram as the phone channel. They left every other choice to us.
- Builds on: [2026-11-11-ostiary-release-design.md](2026-11-11-ostiary-release-design.md). The security model is unchanged except where noted.

## 1. Scope

| # | Feature | Why |
|---|---|---|
| A | Graceful stop and restart | A restart or upgrade today kills running commands and drops pending approvals. |
| B | `strict` profile | Under `standard`, Claude Code's mutating commands are only asked about in the chat. |
| C | One daemon at a time | Two quick app launches can start two daemons (parked item M6). |
| D | Approved port tunnels | Let agents reach a database or other service behind SSH without holding SSH credentials. |
| E | Approve from your phone through Telegram | An agent waiting for approval stalls when the user is away from the computer. |
| F | UX bundle | Log grouped by session, config diff before reload, overview strip, and the parked Minor items from the UX audit. |

Out of scope: hardened mode (agent running as another OS user), code signing, jump hosts, per-project host scoping in the UI. These are candidates for v0.4.

## 2. A: graceful stop

- **Draining state.** On `stop`, `Restart` (upgrade), SIGTERM or SIGINT, the daemon enters *draining*:
  1. New `Exec`, `Job start` and tunnel requests are refused with the new code **103** (`CodeRestarting`). Message: `ostiary is restarting; wait about 10 seconds and retry the same command once`.
  2. The daemon waits for in-flight `Exec` calls to finish, for at most **60 s**. A `--now` flag or `force` skips the wait.
  3. Pending approval requests are finished with outcome `restart`. Agents get 101-like guidance: `the request was cancelled because ostiary restarted; ask the user before retrying`. The audit logs a decision `cancelled` with note `restart`.
  4. Then the listener closes. Jobs and tunnels are killed, and each one is logged.
- **Warning in the UI before restarting.** The upgrade, lock and restart paths show a confirm dialog when something is in flight: `N lệnh đang chạy, M job, K tunnel`. It offers "Chờ xong rồi cập nhật" (drain) and "Cập nhật luôn" (force).
  - The `Status` reply carries `Running {Commands, Jobs, Tunnels int}` for this dialog.
- **Service managers.** The systemd unit gets `TimeoutStopSec=75`. A launchd job gets SIGTERM, then SIGKILL after about 20 s. That is acceptable because most commands are short, and a test covers SIGTERM.
- **CLI.** The CLI retries automatically, once, on 103: it waits 10 s and re-dials. If that fails it prints the guidance.
- **Updated text.** The exit-code tables in the skill, `AGENTS.md` and the MCP server now list 103.

## 3. B: `strict` profile

- **Rank.** `readonly` (0) < `strict` (1) < `standard` (2) < `full` (3).
- **Decide.** Same as `standard`, except that `mutate` returns **Approve** for every agent, Claude Code included, with no soft "ask".
- **Where it shows up.** It is a valid value everywhere profiles are accepted: `hosts.toml`, the repo `.ostiary.toml` caps (where it is stricter than `standard`), the UI segmented control (with the label "strict: mọi lệnh thay đổi đều phải duyệt"), and the docs.

## 4. C: one daemon at a time

- Before `Listen`, the daemon takes an exclusive lock on `state/daemon.lock` and holds it for its whole life.
  - Unix: `flock(LOCK_EX|LOCK_NB)`.
  - Windows: `LockFileEx` with `LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY`.
- If the lock is busy, the daemon exits with the message `daemon already running`.
- The successor started by `--after-pid` waits for the lock instead of polling the socket, for at most 10 s.
- Tests: two locks in one process (via two file descriptors) fail fast, and releasing the first lets the second succeed.

## 5. D: approved port tunnels

- **Configuration.** Each host gets a new field `tunnels = ["127.0.0.1:5432", "db.internal:3306"]`. This is an allow-list of `host:port` targets *as seen from the SSH server*. Empty means no tunnels. The host drawer has a chip input for it.
- **Agent CLI.**
  - `ostiary tunnel open <host> <target> [--ttl 1h]` prints `tunnel 7 127.0.0.1:41873 -> <host>:<target> until 15:42`.
  - `ostiary tunnel list` shows the tunnels.
  - `ostiary tunnel close <id>` closes one.
  - MCP gets the tools `tunnel_open`, `tunnel_list` and `tunnel_close`.
- **Approval.** Opening a tunnel *always* needs human approval: OS dialog, code, UI or Telegram. There is no sticky "30 phút" option.
  - The request shows on approval cards with a new kind `tunnel`, level `destructive`, and the text `mở tunnel tới <target> qua <host> trong <ttl>`.
  - A target that is not in the allow-list is refused with 100 (blocked) before any approval is requested.
- **Runtime.**
  - The daemon listens on `127.0.0.1:0` (a random port). Each accepted local connection is forwarded with `ssh.Client.Dial("tcp", target)` over the pooled connection.
  - TTL: default 1 h, at most 8 h.
  - A tunnel closes on TTL expiry, on `close`, in the UI, or when the daemon drains.
  - Audit records open (approved/denied), close (reason, bytes in and out, connection count) and errors.
- **Known limit, documented.** Any local process of any user can connect to the loopback port while the tunnel is open. The UI and README say so. The TTL keeps the window short.
- **Database passwords** are not handled. The tunnel gives a network path only, and the agent still needs DB credentials. We recommend a read-only DB user.
- **UI.** A new section "Tunnel đang mở" on the Host view lists each tunnel's host, target, local port, time left and traffic, with a "Đóng" button.

## 6. E: Telegram approvals

- **Pairing,** in the UI under *Kho khóa → Telegram*. It is an admin operation `telegram-pair` (Begin→Admin).
  1. The user creates a bot with @BotFather and pastes the token. The token is stored **in the vault** as the secret `telegram-token`.
  2. The daemon calls `getMe` and shows "@<bot>".
  3. The UI shows a 6-digit pairing code. The user sends `/pair <code>` to the bot.
  4. The daemon long-polls `getUpdates`. On a matching code from a private chat, it stores `chat_id` and `user_id` in the vault and replies "Đã kết nối với Ostiary trên <hostname>".
  5. The code is valid for 10 minutes and allows 5 wrong attempts.
- **Unpairing** is the admin op `telegram-unpair`. It deletes the token and the ids.
- **Notifications.** When a request is added, and Telegram is paired and enabled, the daemon sends a message:
  - Header `⚠️ Ostiary #<id> · <level> · <host>`.
  - Then agent, project (repo basename), the command as a monospace block truncated at 3000 chars, the reasons, and the expiry.
  - Inline buttons: "✅ Duyệt 1 lần", "⏱ 30 phút" (only where the UI also allows it), "❌ Từ chối".
  - The callback data is `<id>:<choice>:<nonce>`, where the nonce is 8 random bytes created per request.
- **Accepting a callback** requires all of the following:
  - the update comes from our long poll;
  - `from.id` equals the paired user and `message.chat.id` equals the paired chat;
  - the nonce matches;
  - the request is still pending.
- **Resolving.** The request resolves through `Queue.Resolve` with auth **`telegram`**, which is recorded in the audit. The bot then edits the message to show the outcome ("Đã duyệt bởi bạn qua Telegram lúc 15:02"). A request decided elsewhere also has its message edited ("Đã xử lý trên máy").
- **Settings.**
  - "Cho phép duyệt lệnh phá hủy qua Telegram": on by default. When it is off, destructive messages are informational only and carry no buttons.
  - Tunnels follow the same toggle.
  - Admin operations are **never** approvable through Telegram.
- **Network.** The daemon talks only to `https://api.telegram.org/bot<token>/…` with a 60 s long poll and exponential backoff on errors. Failures show in Sức khỏe ("Telegram: không kết nối được").
- **Privacy note in the UI.** "Nội dung lệnh, tên host và agent sẽ đi qua máy chủ Telegram."
- **Threat note in the README.** Whoever controls the paired Telegram account can approve requests. Users should protect it with Telegram 2FA, and can turn off destructive approval over Telegram.
- **Tests.** The Telegram API is faked with `httptest`. The base URL can be overridden only in tests and in the `e2efake` build. The tests cover:
  - pairing with the right code, wrong codes, expiry, and messages from the wrong chat;
  - a callback with a bad nonce or from the wrong user being ignored;
  - a successful approve and a successful deny;
  - message editing after a decision made elsewhere.

## 7. F: UX bundle

- **Log grouped by session.** Client-side grouping on the Nhật ký view: consecutive entries with the same agent and repo (or cwd), less than 30 minutes apart, form a session.
  - The header shows agent, project, time range, command count, and badges for denied or approved entries.
  - Sessions can be collapsed and expanded.
  - A toggle switches between "Theo phiên" (the default) and "Danh sách".
- **Config diff before "Đọc lại cấu hình".**
  - On every approved save or reload, the daemon keeps a copy of `hosts.toml` and `rules.toml` as last approved, in `state/approved/`, at mode 0600.
  - `GET /api/config/diff` returns a unified diff per file. It uses a simple LCS line diff on the server side, in pure Go, capped at 2000 lines.
  - The reload confirm dialog shows the diff, colour-coded. If no copy exists yet, it says "chưa có bản đã duyệt để so sánh".
- **Overview strip** at the top of the Duyệt view, shown only on wide screens and collapsed on mobile:
  - today's command count by decision (allow, approved, denied or blocked);
  - open tunnels;
  - Telegram status;
  - the last blocked command.
  - It is computed from the audit and status through a new `GET /api/summary`.
- **Parked Minor items from the UX audit** (UX-17, 20, 21, 26–29 and the remaining UX-22 labels):
  - fix the cheap ones;
  - list the rest in the plan's ledger.

## 8. Testing and release

- **Unit tests** for each feature, as listed above.
- **E2E** (`scripts/e2e.py`) gains:
  - a strict-profile check;
  - a tunnel check: open through the fake approval, connect to an echo server behind the e2e sshd, then close;
  - drain behaviour: `stop` while a `sleep 3` runs, so the run finishes and the next request gets 103.
- **Telegram** runs against a fake API in `e2efake` builds only, with `OSTIARY_E2E_TELEGRAM_URL`. CI's marker grep keeps it out of release builds.
- **Release:** `v0.3.0`, through the usual tag flow, signed. Existing installs see the banner.
